# 生产环境权限管理照做清单（创建 · 授权 · 回收 · 审计）

> 依据官方文档：[内置鉴权 RBAC](https://doris.apache.org/zh-CN/docs/4.x/admin-manual/auth/authorization/internal/)（2026-05 更新）、[GRANT TO 语法](https://doris.apache.org/zh-CN/docs/4.x/sql-manual/sql-statements/account-management/GRANT-TO/)（2026-10 更新）、[数据访问控制](https://doris.apache.org/zh-CN/docs/4.x/admin-manual/auth/authorization/data/)、[身份认证](https://doris.apache.org/zh-CN/docs/4.x/admin-manual/auth/authentication/)、[审计插件](https://doris.apache.org/zh-CN/docs/4.x/admin-manual/audit-plugin/)。
> 适用：4.0.x / 4.1.x。语法差异处已标注。
> 每条同样是：做什么 → 为什么 → SQL → 期望结果 → 不对怎么办。

::: warning 先说清楚一件事
Doris 官方**没有**一节"从头到尾讲权限管理"的视频课（截至 2026-11）。这个主题的正确做法是：**照官方文档写 SQL，用视频只建立界面感**。本文把文档里的权限表、层级、最佳实践，整理成一套可以直接在生产执行的顺序。

## 0. 四条原则（定不下来就别动手）

| 原则 | 落到动作上 |
|---|---|
| **最小权限** | 只给业务真正需要的库表权限，不给库级就不给全库 |
| **角色化，不直授用户** | 权限绑角色，人绑角色；人走了撤角色，权限不重配 |
| **可审计** | 每次变更留记录；审计日志必须开 |
| **双人复核** | 生产加/删权限前，SQL 先在测试集群跑一遍，再经第二人确认 |

**为什么强调角色化**：Doris 支持 `GRANT ... TO 'user'@'%'` 直接给用户授权，但底层会为每个用户建一个隐藏的默认角色。人一多，你根本说不清"谁到底有什么权限"。**统一用角色，只用 `SHOW ROLES` + 角色成员就能看懂全貌。**

## 1. 模型速查（3 分钟看懂 RBAC）

```text
用户 (user@host)  ──持有──►  角色 (role)  ──拥有──►  权限 (privilege)
                                      └──► 作用在：Catalog / 库 / 表 / 列 / Resource
```

### 1.1 你只会用到这 6 个权限

| 权限 | 能干什么 | 给谁 |
|---|---|---|
| `SELECT_PRIV` | 读（select、show） | 所有查询方 |
| `LOAD_PRIV` | 写入（load、insert、delete） | 数据开发 / 导入任务 |
| `ALTER_PRIV` | 改表结构、加删列、改分区 | 数据开发 |
| `CREATE_PRIV` | 建库建表 | 数据开发 |
| `DROP_PRIV` | 删库删表 | **默认不给**，按需临时给 |
| `GRANT_PRIV` | 给别人授权 | 业务管理员（按库粒度） |

另外 4 个（`ADMIN_PRIV`、`NODE_PRIV`、`USAGE_PRIV`、`SHOW_VIEW_PRIV`）见第 5 节红线。

### 1.2 授权层级（写 SQL 时决定作用范围）

| 作用范围 | 写法 | 用在什么场景 |
|---|---|---|
| 全局 | `ON *.*.*` | 极少用，等于全集群 |
| 某 Catalog 全部库 | `ON internal.*.*` | 基本不用 |
| 某库全部表 | `ON internal.db_report.*` | **最常用** |
| 单表 | `ON internal.db_report.t_order` | 敏感表单独控制 |
| 单表的某几列 | `SELECT_PRIV(c1,c2) ON internal.db.t` | 手机号、身份证等敏感列 |

::: tip 一个容易写错的点
4.x 的库表路径是**三段**：`catalog.db.table`。默认 catalog 叫 `internal`，所以写 `internal.db_report.*` 是对的；只写 `db_report.*` 在多数版本也能识别，但生产建议写全，避免以后接外部 Catalog 时歧义。
自 4.1.5 起，对象名最多三段，多于三段会被直接拒绝。
:::

## 2. 生产角色矩阵（照着建，4 个角色够用）

先和业务方把这张表定下来，再动手建。**不要边建边想。**

| 角色名 | 权限 | 作用范围 | 谁持有 | 说明 |
|---|---|---|---|---|
| `role_ops_admin` | `NODE_PRIV` + `ADMIN_PRIV` | 全局 | DBA / 运维（≤3 人） | 只在集群维护时激活，日常不用 |
| `role_biz_admin` | `GRANT_PRIV` + 全套读写 | **单库** | 每个业务线的数据负责人 | 由他管理本业务的账号，无需 DBA 介入 |
| `role_dev_rw` | `SELECT/LOAD/ALTER/CREATE` | 单库 | 数据开发 | 不给 `DROP_PRIV` |
| `role_bi_ro` | `SELECT_PRIV` | 单库 | BI、报表、临时查询 | 只读 |

**为什么把业务管理员单独拆出来**：官方"场景二：多业务集群委托管理"就是这么设计的——管理员给每个业务库一个拥有**库级 `GRANT_PRIV`** 的用户，该用户只能在自己库里给人授权。这样 DBA 不用天天给新人开账号，业务间也天然隔离。

## 3. 创建流程（8 步，生产可直接执行）

### 3.1 准备：用一个专用的"权限管理员"账号干活

```sql
-- 用 root 登录后，先建一个管理账号（不要日常用 root）
CREATE USER 'dba_admin'@'10.20.30.%' IDENTIFIED BY '换成强密码';
GRANT 'admin' TO 'dba_admin'@'10.20.30.%';
SHOW GRANTS FOR 'dba_admin'@'10.20.30.%';
```

**为什么**：`root` 是内置超管，密码一旦泄露等于集群沦陷，而且 root 的操作在审计里和其他账号混在一起。生产惯例是 root 只留作应急（密码封存），日常用实名管理账号，**审计日志里能直接看到是谁改的**。

**期望结果**：`SHOW GRANTS` 里能看到 Role `admin`。

::: warning 3.1 的 host 一定要写网段
`@'10.20.30.%'` 表示只有这个网段能连。写成 `@'%'` 等于全世界可连，只要密码被猜中就能进。**生产禁止 `@'%'`**，除非是容器化、来源 IP 不固定的场景，那时也要配合网络策略。
:::

### 3.2 建角色

```sql
CREATE ROLE 'role_bi_ro';
CREATE ROLE 'role_dev_rw';
CREATE ROLE 'role_biz_admin';
SHOW ROLES;
```

**期望结果**：`SHOW ROLES` 里出现这三行（另有内置的 `admin`、`operator`）。

### 3.3 给角色授权（关键一步）

以报表库 `db_report` 为例：

```sql
-- 只读角色：整个库可查
GRANT SELECT_PRIV ON internal.db_report.* TO ROLE 'role_bi_ro';

-- 开发角色：查 + 写 + 改结构 + 建表（不给删库删表）
GRANT SELECT_PRIV, LOAD_PRIV, ALTER_PRIV, CREATE_PRIV
  ON internal.db_report.* TO ROLE 'role_dev_rw';

-- 业务管理员：本库全部权限 + 本库的授权能力
GRANT SELECT_PRIV, LOAD_PRIV, ALTER_PRIV, CREATE_PRIV, DROP_PRIV, GRANT_PRIV
  ON internal.db_report.* TO ROLE 'role_biz_admin';

-- 敏感表：只给部分列（仅支持 SELECT_PRIV）
GRANT SELECT_PRIV(order_id, city, amount) ON internal.db_report.t_order TO ROLE 'role_bi_ro';
```

**语法要点**：给**角色**授权时，必须写 `TO ROLE '角色名'`；给**用户**授权才是 `TO '用户'@'host'`。少写 `ROLE` 会被当成用户身份报错。

**期望结果**：每条返回 `Query OK`。

::: tip 权限可叠加，不可"抵消"
同一角色上多层级的 `SELECT_PRIV` 是**并集**。你没法用"给整库只读 + 对某表收回"来实现"整库读但排除一张表"——要用列级授权反向构造，或者把敏感表拆到独立库。
:::

### 3.4 建用户

```sql
CREATE USER 'bi_zhangsan'@'10.20.30.%' IDENTIFIED BY '强密码放这里';
CREATE USER 'dev_lisi'@'10.20.30.%' IDENTIFIED BY '强密码放这里';
```

**为什么要 `@host`**：Doris 的用户身份是 `用户名 + 来源 host` 两部分。`bi_zhangsan@10.20.30.%` 和 `bi_zhangsan@%` 是**两个不同用户**，权限互不相通——这是新手最容易踩的坑：给 `@'%'` 授了权，用 `@'10.20.30.%'` 登录却提示没权限。

### 3.5 把角色给用户

```sql
GRANT 'role_bi_ro' TO 'bi_zhangsan'@'10.20.30.%';
GRANT 'role_dev_rw' TO 'dev_lisi'@'10.20.30.%';
```

**期望结果**：`Query OK`。

**为什么要分成"角色授权"和"角色分配"两步**：这样同岗位的新人入职只需最后这一条，前面所有权限配置直接复用。

### 3.6 验证（不做这步等于没交付）

```sql
SHOW GRANTS FOR 'bi_zhangsan'@'10.20.30.%';
```

期望能看到 Role `role_bi_ro` 及其包含的权限。

**再用新账号真连一次**（不要只看 SHOW 结果）：

```bash
mysql -ubi_zhangsan -p -P9030 -h<FE_IP>
```

```sql
SHOW DATABASES;                                  -- 期望：能看到 db_report
SELECT COUNT(*) FROM db_report.t_order LIMIT 1;  -- 期望：能查
INSERT INTO db_report.t_order VALUES (...);      -- 期望：报错（只读角色不该能写）
```

**越权测试才是验收**：只验证"能查"不够，还要验证"不能写"。

### 3.7 交付给使用人

交付时说清楚 4 件事，避免反复被问：

1. 连接地址：`<FE_IP>:9030`，用户名带不带 host（很多客户端只让填用户名，实际匹配的是 `用户名@来源IP`）；
2. 能用哪些库；
3. 只读还是可写；
4. 密码修改方法：`SET PASSWORD = PASSWORD('新密码');`

### 3.8 记录（合规要求）

把这次变更写进台账：日期、申请人、账号、角色、库表范围、批准人、变更单号。**没有台账，半年后没人说得清某个账号为什么有 DROP 权限。**

## 4. 日常管理动作

| 频率 | 动作 | SQL |
|---|---|---|
| 每周 | 新建账号按第 3 节流程走，禁止临时直授 | — |
| 每月 | 权限巡检：导出所有用户-角色-权限 | `SHOW ALL GRANTS;` |
| 每月 | 查僵尸账号（长期未登录） | 看审计日志（第 6 节） |
| 人员离职 | 先 `REVOKE` 角色，验证业务无影响，再删用户 | 见 4.1 |
| 业务下线 | 撤库级权限，确认无人使用后删库 | — |

### 4.1 回收权限（顺序很重要）

```sql
-- 1) 先撤角色（立刻生效，可随时加回）
REVOKE 'role_dev_rw' FROM 'dev_lisi'@'10.20.30.%';

-- 2) 确认业务没人用了，再删用户
DROP USER 'dev_lisi'@'10.20.30.%';
```

**为什么先撤角色再删用户**：撤角色是可逆的，删用户不可逆。先撤、观察一天，确认没有定时任务在跑，再删。

::: warning 删角色 ≠ 删用户
`DROP ROLE 'role_bi_ro';` 会让**所有持有该角色的用户当场失去权限**。生产上删角色前，先 `SHOW GRANTS FOR` 逐个确认持有人，或先 `REVOKE` 把人都摘干净。
:::

## 5. 六条红线（生产必看）

| 红线 | 为什么 |
|---|---|
| **`NODE_PRIV` 只给运维，绝不给业务** | 它能上下线 BE 节点，等于能停掉整个集群的存储 |
| **`ADMIN_PRIV` 要当成 root 看待** | 它是"除节点管理外的全部权限"，含建用户、建库、删表 |
| **`GRANT_PRIV` 不要给全局** | 只给到**库级**，否则对方能给自己开任何权限 |
| **`@'%'` 慎重** | 等于不限来源，密码泄露即失守 |
| **`DROP_PRIV` 默认不给** | 真需要时临时给，用完撤 |
| **root 日常不用** | 只作应急，密码封存、用后即改 |

另外，列权限目前**只支持 `SELECT_PRIV`**——想限制"能看表但不能看手机号列"，只能靠列级 SELECT + 拆分表实现，不能靠"给写权限但不给某列"。

## 6. 审计：怎么知道"谁在什么时候改了什么"

1. **开审计插件**：按[审计插件文档](https://doris.apache.org/zh-CN/docs/4.x/admin-manual/audit-plugin/)配置，插件会把 SQL 操作落到审计表/文件；
2. **重点看三类事件**：`GRANT` / `REVOKE` / `CREATE USER|ROLE`（权限变更）、`DROP`（破坏性操作）、异常来源 IP 的登录失败；
3. **可视化看**：SelectDB Studio 有审计日志面板，可直接筛选用户与时间（见第 8 节视频）；
4. **权限基线核对**：每月把 `SHOW ALL GRANTS;` 导出存档，和上月 diff，非预期变化立刻查。

## 7. 常见报错对照

| 现象 | 根因 | 处理 |
|---|---|---|
| `Access denied for user 'x'@'y'` | 用户或 host 不匹配 | 确认建的是 `x@y`，不是 `x@%` |
| 登录成功但看不到库 | 没给该库权限，或给了别的 host | `SHOW GRANTS FOR 'x'@'精确host';` |
| `GRANT` 报语法错 | 给角色授权漏了 `ROLE` | 写 `TO ROLE 'role_x'` |
| `errCode = 2, detailMessage = Access denied; you need (at least one of) the GRANT_PRIV` | 操作者自己没有对应授权能力 | 用 `dba_admin` 执行，或给操作者库级 `GRANT_PRIV` |
| 授予后立刻不生效 | host 写成域名，权限有约 1 分钟延迟 | 等 1 分钟，或改用 IP 网段 |
| 建表报没权限，但 SELECT 正常 | 缺 `CREATE_PRIV` | 按 3.3 补 |
| 删除角色后业务中断 | 该角色被多个用户持有 | 重建角色并重新 `GRANT`，回收前先确认持有人 |

## 9. 变更记录模板

```markdown
## 2026-11-XX 权限变更 · <业务线>

- 申请人 / 批准人：
- 变更类型：新建账号 / 加权限 / 撤权限 / 删账号
- 账号：<user>@<host网段>
- 角色：<role>
- 范围：internal.<db>.<table>（如仅某表请写明）
- 执行人 / 执行时间：
- 验证结果：能查 <表> ；不能写（已测）
- 回滚方式：REVOKE '<role>' FROM '<user>'@'<host>'
```
