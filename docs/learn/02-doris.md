# 02 · FE 与 BE，谁在忙什么？

> 约 12 分钟 · 无需任何环境 · 有一张可以点的交互图

上一课我们知道：Doris 擅长“大范围数据的汇总分析”。这一课看它内部怎么分工。
先记住一句定盘星：**FE 管“想清楚怎么做”，BE 管“真的去做”。**

## 一个类比：前台与后厨

<details class="say-plain">
<summary>先用白话理解（点开）</summary>

把 Doris 想成一家餐厅：

- **FE（Frontend）= 前台**：接待客人（接收请求）、看懂菜单上这道菜该怎么做（解析与规划）、记着店里所有的账本和座位表（元数据）、盯着后厨谁在忙（节点管理）；
- **BE（Backend）= 后厨**：真的存放食材（存储数据）、真的炒菜（执行计算）。灶越多，出菜越快——所以 BE 可以有好多台。

客人从来不用进后厨，只跟前台打交道；你平时连 Doris，连的也是 FE。

</details>

## FE 的四项职责

| 职责 | 它在干什么 | 运维时你会在哪碰到它 |
|------|-----------|----------------------|
| 用户请求接入 | 兼容 MySQL 协议，客户端直接连它 | 配连接串、查连接失败 |
| 查询解析与规划 | 读懂 SQL，生成执行计划，决定任务怎么分 | 排查慢查询（看执行计划） |
| 元数据管理 | 库表结构、副本分布、用户权限、集群拓扑 | 改表、授权、查节点状态 |
| 节点管理 | 心跳检测、副本修复、扩缩容调度 | 看 BE 上下线、做扩容 |

FE 的元数据由内置的 BDB JE 引擎存储，不依赖 ZooKeeper 之类的外部组件——这也是 Doris 部署相对简单的原因之一。

<details class="say-plain">
<summary>“BDB JE 引擎”是什么？（点开，30 秒看懂）</summary>

- **它解决什么问题**：FE 的账本（元数据）不能只放在一台机器的内存里——机器一挂，整个集群就“失忆”了。所以每次改账本，都要安全地写入磁盘，并同步给其他 FE，多数派确认后才算数；
- **BDB JE 是什么**：Doris 内置的“记账组件”（Berkeley DB Java Edition），专门干这件事——把每条元数据改动记成日志、复制到多数派 FE。上表说的“多数派确认”就是它实现的；
- **“不依赖 ZooKeeper”是什么意思**：很多分布式系统（如 HBase）要额外装一套 ZooKeeper 集群来做这类协调；Doris 把这个能力内置了，所以装好 FE 就行，不用先装别的。

> 一句话：**BDB JE = FE 自带的可靠记账本**，现在理解到这里就够。深入场景在后面：FE 扩缩容与多数派见「02 · 部署与变更」，bdbje 目录位置、元数据备份恢复见「04 · 备份恢复与容灾」。

</details>

## FE 的三个角色

生产环境会部署多个 FE 保证高可用，它们分工如下：

| 角色 | 干什么 | 参与选主？ |
|------|--------|-----------|
| Master | 负责元数据的写入，并同步给其他角色 | 是 |
| Follower | 持有元数据副本；Master 故障时参与选举新主 | 是 |
| Observer | 只读元数据，用来分担查询压力 | 否 |

元数据的每次变更需要**多数派节点确认**才生效，这是 FE 侧一致性的底线。

> 注意：你的测试机是 **1 个 FE**，所以它“既是 Master 也是全部”。这是学习用配置，生产不会这么部署。

## BE 的四件武器

| 能力 | 一句话解释 |
|------|-----------|
| 列式存储 | 数据按列存放，查询只读需要的列，省 IO |
| Tablet | 数据被水平切成一个个分片，Tablet 是调度的最小单位（下一课细讲） |
| 多副本 | 每个 Tablet 默认存 3 份，坏一台不丢数据 |
| 向量化 + Pipeline 执行 | 按列批量算、多核并行，官方称宽表聚合可快 5~10 倍 |

## “存算一体”是什么意思？

交互图右上角标注了“存算一体”，它指**数据存在哪台机器，计算就在哪台机器做**——BE 既存数据又跑计算，读写都走本地磁盘，性能最直接。这是 Doris 的经典模式，你们的生产集群（ECS 自建）就是它。

它有个“新亲戚”叫**存算分离**（Doris 3.0 起支持）：数据统一放在对象存储（如 S3）里，计算节点不长期持有数据，按需拉取并用缓存加速——好处是扩缩容便宜灵活，代价是依赖对象存储和网络质量。**初学阶段分清这两个词就够了，你们的环境用的是存算一体。**

## 集群可以几台 FE、几台 BE？

**数量各自独立，没有配比要求。**常见组合：

| 组合 | 合法？ | 说明 |
|------|--------|------|
| 1 FE + 1 BE | ✅ | 你的测试机：能学完整流程，但建表副本数只能设 1（默认 3 副本放不下） |
| 1 FE + 3 BE | ✅ | 交互图里画的这个：恰好放满默认 3 副本，是体验副本机制的最小集群；FE 单点，只适合测试 |
| 3 FE + N BE | ✅ | 生产推荐：FE 一主两从保证元数据高可用，BE 按数据量扩展 |

所以扩容时先想清楚目的：加 **BE** 是为了“装更多数据、算得更快”；加 **FE** 是为了“高可用、分担查询压力”——两条线各管各的。

## 两个容易误解的地方

<details class="say-plain">
<summary>追问：备份时 FE/BE 是每台机器都备一份吗？（点开，权威答案）</summary>

都不是。Doris 的备份**不按“台”算，按“数据”算**：

- **FE（以 3 台为例）**：3 个 FE 的元数据由 BDB JE 保持实时一致、**互为副本**——备份元数据只需从 Master 处拿一份，3 台各备一遍是重复劳动；
- **BE（以 3 台为例）**：数据按 Tablet 切分、每片 3 副本分散在不同机器。官方备份是一条 SQL（`BACKUP SNAPSHOT ... TO 仓库`）：给指定库/表/分区拍快照，**每个分片只导出一份**到远程存储（S3 / HDFS / MinIO 等）。反过来逐台拷 BE 磁盘既重复（同一份数据拷 3 次）又不完整（单台 BE 只持有部分分片）；
- **最容易搞混的一点**：**3 副本 ≠ 备份**。副本防的是“坏一台机器”；备份防的是“误删表、整集群损毁”——`DROP TABLE` 会同时删掉全部 3 个副本，副本救不了你，只有集群外的备份能救。

> 权威依据：官方 4.x 文档《备份》（2026-10 更新）——备份以快照形式写入**远程存储**、用于灾难恢复；目前仅支持全量备份，且存算分离模式暂不支持备份/恢复。建仓、BACKUP/RESTORE 命令、元数据备份的完整实操，在「04 · 备份恢复与容灾」主题细讲。

</details>

::: warning 误解 1：FE 负责汇总计算
不对。**汇总计算主要发生在 BE**——BE 各自算好自己那部分，必要时 BE 之间再交换中间结果，最后由一个执行节点汇聚出最终结果。结果随后回传 FE，FE 再转交客户端：FE 在回程里只是“收发室”，负责对接和转交，不是计算主力。
:::

::: warning 误解 2：FE 里存着业务数据
不对。FE 存的是**元数据**（账本：有哪些表、分片在哪台机器），真正的明细数据全在 BE。所以监控里“FE 磁盘告警”和“BE 磁盘告警”是两回事。
:::
