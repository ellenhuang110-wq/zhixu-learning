# 03 · 数据到底是怎么放的？

> 约 12 分钟 · 无需任何环境 · 用例子理解

上一课说 BE 负责存数据。这一课回答一个对运维极其重要的问题：**数据在 BE 里是怎么摆放的？**
摆放方式直接决定查询快不快、扩缩容难不难、磁盘满的时候该清哪里。

## 一个类比：档案柜

<details class="say-plain">
<summary>先用白话理解（点开）</summary>

把一张表想成一组档案柜：

- **表（Table）= 整组柜子**：比如“监控告警表”；
- **分区（Partition）= 抽屉**：通常按时间分，10 月一抽、11 月一抽；
- **分桶（Bucket）= 抽屉里的文件夹**：把同一抽屉的档案再均匀打散成若干份；
- **Tablet = 文件夹本身**：真正放在某台 BE（柜子管理员）手里的物理分片。

查数据时，先决定开哪个抽屉（按时间），再在抽屉里翻对应的文件夹——而不是把整组柜子翻个底朝天。

</details>

## 官方定义的流向

Doris 用**分区 + 分桶**两层方式组织数据，数据流向是：

```text
表 ──► 分区（按列值切，如时间）──► 分桶（再打散）──► Tablet（物理分片，存在 BE 上）
```

两个层次各管一件事：

- **分区**面向“管理”：按时间或枚举值切分（Range / List 两种），方便按时间段查询、归档、清理；
- **分桶**面向“均匀与并行”：常用 Hash 分桶（按分桶列算哈希再取模），把数据均匀铺到多个 Tablet 上，让多台 BE 能同时干活。

## 写入与查询，各走一遍

以 `按日期分区 + 按 user_id 分桶` 的表为例：

**写入时**：一行数据先按日期落进对应分区（比如 `2026-10-21` 进 10 月分区），再按 user_id 的哈希值落进该分区的某个 Tablet。

**查询时**：`WHERE date = '2026-10-21'` 会让优化器**只扫描这一天所在的分区**，其余分区直接跳过——这叫**分区裁剪**，是大数据量下最重要的省时手段。数据越大，省得越多。

## 副本：同一份档案，放三处

每个 Tablet 默认保存 **3 个副本**，分布在不同的 BE 上：

- 写入时需要**多数派**（比如 3 份里的 2 份）确认成功，才算写成功；
- 某台 BE 故障时，副本还在别的机器上，集群会检测到并从健康副本补齐。

这就是为什么生产集群挂一台 BE 通常无感，而**单机 1 副本的测试环境不能验证这一点**——学原理时知道机制，演练时再申请多节点资源。

## 列式存储：只翻需要的列

Doris 是列式存储：数据按列组织、编码、压缩。配合台账例子理解——

查询“各系统告警数量”只需要 `系统名称` 和 `告警时间` 两列，列存就**只读这两列的数据**，其余几十列（责任人、备注、详情……）碰都不碰。列越多、表越宽，省得越明显。

## 两条值得背下来的设计经验

来自官方文档的通用建议，以后做建表评审、排查问题时都用得上：

1. **分区列优先选时间或低基数枚举**（日期、地区），方便裁剪和管理；
2. **分桶列选高基数列**（如 user_id），让数据均匀打散，避免个别 Tablet 过热。

::: tip 一句话带走
**表 → 分区 → 分桶 → Tablet：分区管“好查好清理”，分桶管“均匀与并行”，Tablet 默认三副本管“坏一台不丢”。**
:::
